# 全域使用者管理搜尋設計

## 目標

在全域使用者管理頁 `/admin/users` 增加使用者搜尋與所屬專案篩選，讓管理員能從姓名、Email 或專案名稱快速找到成員，同時保留現有角色直接修改、編輯與刪除功能。

## 範圍

### 包含

- 在使用者列表上方提供關鍵字搜尋欄位。
- 關鍵字比對使用者姓名、Email，以及所屬專案名稱。
- 提供所屬專案下拉篩選，包含「全部專案」與所有專案。
- 以 URL query parameters 保存查詢條件，支援重新整理與分享結果網址。
- 無結果時顯示明確的空結果訊息。
- 保留現有角色下拉直接修改、編輯與刪除行為。

### 不包含

- 不新增資料表或 migration。
- 不新增獨立搜尋 API。
- 不改變角色、權限或自我帳號保護規則。
- 不改變站點成員管理頁的搜尋行為。

## 使用者介面

- 關鍵字欄位標示為「搜尋姓名、Email 或專案名稱」。
- 專案篩選欄位標示為「所屬專案」。
- 提供「搜尋」與「清除」操作。
- 使用 GET 表單送出查詢，查詢條件使用 `q` 與 `site` 參數。
- 查詢結果仍使用現有列表欄位：姓名、電子郵件、角色、所屬專案、註冊時間與操作。

## 查詢與資料流

1. Server Component 讀取頁面的 `searchParams`。
2. 將關鍵字 trim；空字串視為未設定。
3. 載入可供篩選的專案清單。
4. 使用 Prisma `user.findMany` 建立條件：
   - `q` 存在時，以大小寫不敏感方式比對 `name`、`email`。
   - `q` 也比對關聯 `sites.site.name`，使專案名稱可被搜尋。
   - `site` 為有效專案 ID 時，以 `sites.some.siteId` 限定所屬專案。
5. 查詢結果依現有 `createdAt desc` 排序。
6. 將目前查詢條件回填至表單，避免重新整理後遺失。

專案名稱的搜尋與專案下拉篩選可同時使用，結果必須同時符合兩者。

## 錯誤與邊界行為

- 未設定查詢條件時，顯示全部使用者。
- 不存在或非數字的 `site` 參數視為未選擇專案，不因查詢參數導致頁面錯誤。
- 搜尋無結果時保留表頭並顯示「找不到符合條件的使用者」。
- 角色更新、編輯與刪除的錯誤處理維持現有行為。

## 測試策略

- 新增頁面契約測試，確認搜尋表單、`q`/`site` query parameters、專案選項與空結果訊息存在。
- 新增或調整使用者列表查詢測試，確認：
  - 姓名或 Email 關鍵字會建立對應條件。
  - 專案名稱關鍵字會透過關聯條件查詢。
  - 專案 ID 篩選會限制所屬專案。
  - 無效專案 ID 不會造成例外。
- 執行相關測試，再執行完整測試套件與 lint。

## 實作限制

- 只修改全域使用者管理頁與其必要測試/查詢輔助程式。
- 不改動既有 API 與資料模型。
- 保持既有 dirty worktree 內容不被覆蓋；本次只提交本設計文件。
